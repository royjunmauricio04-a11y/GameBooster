# GameBooster v0.3 operations guide

This branch adds four opt-in systems: smart server switching, backup-route circuit breaking, local session history, and an in-game telemetry overlay. The implementation is intentionally conservative: smart switching and the overlay are off by default, and switching can interrupt an active game while the WireGuard tunnel is re-established.

## Before testing

Run the Android unit tests and debug build through GitHub Actions before installing an APK. The v0.3 code was supplied as an uncompiled change set, so the first CI run is the authoritative compile check. Test first on a spare device and a non-competitive game. Do not enable the overlay for a game whose anti-cheat policy prohibits overlay tools.

Use only authorized GameBooster gateways. The app does not discover or adopt arbitrary public IP addresses. Each server must already be a trusted row in `public.servers`, with a working WireGuard endpoint, gateway API, public key, and health-check path.

## Smart switching

Smart switching is disabled by default. When enabled in Diagnostics/Settings, the app watches live TCP-connect samples while connected. After three consecutive bad samples—loss, no response, or a latency regression—the app measures alternative servers through the physical network rather than through the active tunnel. It switches only when an alternative clears the policy margin. The current defaults are a two-minute switch cooldown, a one-minute re-evaluation interval, and a minimum improvement of 20 ms plus 25 percent.

These are starting values, not universal truths. Tune them with real device data. A switch can interrupt a game for several seconds, and TCP-connect measurements are not the same as the game’s UDP latency.

## Backup routes and circuit breaker

A server with two qualifying failures is skipped for five minutes, then receives one trial. Reconnect chooses the best healthy backup instead of repeatedly retrying a tripped route. This is failover, not multi-hop VPN. The current gateway agent does not implement gateway-to-gateway WireGuard forwarding, so no claim of chained routing should be made in the UI or release notes.

## Session history

History is stored on the device as JSON lines, capped at the last 200 sessions, and is wiped on sign-out. A best-effort numbers-only summary can be inserted into `public.session_summaries`; it contains aggregate latency, jitter, loss, duration, switches, reconnects, and byte counters, but no token, key, email, or IP address.

If the base GameBooster schema is already installed, run only the `session_summaries` block at the end of `supabase/schema.sql` in the Supabase SQL editor. If the schema is being installed for the first time, run the complete file. Confirm that the table has RLS enabled and that the three owner policies exist. Do not put a service-role key in the APK or browser.

## Overlay permission

The overlay is off by default. To use it, enable **Display over other apps** for GameBooster in Android system settings, then turn on the overlay in the app. The HUD is draggable and shows ping, jitter, and loss. Android may restrict overlays, and some games or anti-cheat systems may treat overlay tools as unsupported. Turn it off immediately if a game warns about overlays or if input behavior changes.

## Battery and privacy

When the app is hidden, the v0.3 implementation still performs a light three-sample probe every 60 seconds so that history does not become empty. Smart switching probes more often, and the overlay uses the most frequent cadence. Disable both options when you do not need live telemetry. Diagnostics and uploaded summaries must remain redacted; never include access tokens, private keys, email addresses, or full gateway credentials in logs or support exports.

## Release checklist

The safe sequence is: run `:app:testDebugUnitTest` and `:app:assembleDebug` in GitHub Actions; review the test output; install on a spare Android device; test permission denial, sign-out history wipe, network change, failed gateway, reconnect, and overlay off/on; then deploy the Supabase migration if history upload is wanted. Only after those checks should this branch be merged and packaged as a release.
